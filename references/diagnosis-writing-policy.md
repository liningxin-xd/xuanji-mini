# 告警诊断文案规范

本文只约束最终 JSON 中面向用户展示的渠道无关文字，不定义指标、查询、归因算法、候选门槛、调查状态或证据强度。先按指标知识库和 Playbook 冻结结构化事实，再按本文撰写文字；不得执行独立的二次润色，也不得为改善措辞新增查询或改变分析结果。公开字段结构见 [Public Analysis v5](public-analysis-v5.md)。

## 适用字段

本规范适用于：

```text
summary
top_findings[].finding
counterfactual.finding
finding
evidence_limits[]
recommended_action
reason
action
```

字段名、状态、实体标签、日期、数值和单位仍以结构化分析结果为准。措辞调整不得增删候选、改变贡献或反事实数值、扩大因果强度，或把未执行的检查写成已经完成。

## 写作顺序

1. 冻结调查状态、指标、日期、数值、候选、反事实和证据限制。
2. 先写整体 `summary`，再写每个候选和反事实的 `finding`。
3. 根据已冻结的证据写 `recommended_action` 或受阻状态的 `action`。
4. 对全部用户可见文字执行本文末尾的自检；只改文字，不回写分析事实。

## 共同原则

- 直接、克制、具体。先写已经确认的范围，再写仍需核查的方向。
- 区分事实、算术解释和排查建议，不用语气把相关性升级为因果。
- 使用业务可识别的名称。标准指标使用知识库名称，具体游戏或切片使用结果中的 `label` 或 `value`，不得自行起别名。
- 同一句中首次出现对象时写出完整名称；只有已经在该句中明确命名后，才可使用不会产生歧义的简称。
- 不使用责备用户、客户端团队或业务团队的口吻。描述可观测事件和待核查环节，不推测主观意图、责任归属或未观测行为。
- 不用安抚性、夸大性或命令式套话。避免“显然”“肯定”“务必”“严重故障”等证据未支持的表述。

## 独立可读

调用方可能单独突出展示 `recommended_action`，因此该字段必须脱离 `summary` 和 `top_findings` 也能读懂。

- 已定位一个具体游戏或切片时，直接写出它的 `label` 或 `value`。
- 涉及多个对象时，逐一写出需要行动的对象；若对象较多，明确写维度与范围，不用“这些游戏”代替未展示的名单。
- 没有合法候选时，写出标准指标和需要继续观察或复核的范围，不得暗示存在一个已定位但未命名的对象。
- 受阻调查的 `action` 写出缺少的定义、数据、权限或数据源，以及由谁或在哪个范围补充；不写“请继续处理该问题”。

`recommended_action` 和受阻状态的 `action` 禁止使用以下未在同一句中绑定对象的指代：

```text
该游戏
该切片
该指标
该方向
上述对象
对应团队
```

示例：

```text
不推荐：优先核查该游戏的下载链路、版本与终态分布。
推荐：优先核查诡秘之主的下载链路、版本与终态分布。

不推荐：建议对应团队继续核查该方向。
推荐：建议下载链路维护方复核下载人为停止率的终态分布与版本变化。

不推荐：继续跟踪该指标及其恢复条件。
推荐：继续跟踪下载安装完成率，并复核连续窗口和恢复条件。
```

## 字段要求

### summary

- 写明标准指标、告警是否复现、相对基线的方向和综合判断。
- `no_dominant_slice` 时明确是既有异常延续、未达到新增恶化门槛，还是完成规定检查后没有合法候选。
- 不在 `summary` 中伪造切片，不重复罗列全部查询过程。

### finding

- `top_findings[].finding` 写明具体切片名称、当前与基线变化及其对总体的不利影响。
- `entrant/exit` 只描述新增或退出流量的结构影响，不写成切片自身表现恶化。
- `counterfactual.finding` 写明被剔除的具体对象和剔除后的变化，只表达算术解释力。

### evidence_limits

- 只写会影响结论解释的真实边界，说明什么尚不能确认。
- 不把正常业务背景、未触发的可选检查或通用免责声明机械地填入每条结果。

### recommended_action 与 action

- 以可执行动词开头，例如“核查”“复核”“跟踪”“补充”。
- 写清对象、环节和观察目标；存在优先级时先写最有证据支持的方向。
- 使用“核查”“排查”“验证”等不确定性匹配的词，不把建议写成已确认根因或修复指令。

## 用户措辞表

只维护已经确认会影响理解或接受度的表达，不从单个反馈推导无关的普遍禁词。

| 避免表达 | 推荐表达 | 原因 |
|---|---|---|
| 未绑定对象的“该游戏/该切片/该方向” | 具体游戏、切片或排查环节名称 | 独立展示时缺少指代对象 |
| “对应团队继续核查” | 明确维护方或明确核查环节 | 行动对象和范围不清楚 |
| “说明/证明某机制是根因” | “提示优先核查某机制” | 定位证据不能升级为因果确认 |

## 输出前自检

- 每个突出展示的行动字段是否不看上文也能理解？
- 游戏、切片、指标和排查环节是否使用了结构化结果中的明确名称？
- 是否保留了全部日期、数值、方向、状态和证据强度？
- 是否把相关性、反事实或时间共现写成了根因？
- 是否出现未绑定对象的代词、责任暗示或用户不易理解的内部术语？
- 是否只调整文字，没有新增查询、候选、字段或分析事实？
- 是否没有出现 CardKit、主卡、副卡、回复卡、线程、分页、预算、destination 或发送状态等渠道概念？
